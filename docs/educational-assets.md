# Educational assets

The educational-asset foundation stores Kitabu-controlled copies of reviewed learning media. Each asset has a SHA-256 content identity, a local storage key, and immutable provenance.

Source URLs are provenance only. They must never be used as learner-serving URLs; learner delivery uses the authenticated Kitabu-controlled file route documented below.

Only CC0/public-domain, MIT, BSD-2-Clause, BSD-3-Clause, Apache-2.0, and CC BY assets are production eligible after approval. CC BY-SA is retained as restricted and cannot be served in production. CC BY, BSD, and Apache attribution requirements are enforced. Non-commercial, no-derivatives, all-rights-reserved, proprietary, missing, and unverifiable licenses are not production eligible.

CC BY-SA 3.0/4.0 is the only Tier-C restriction currently retained by the normal importer. Restricted candidates receive `usage_restriction = 'share_alike'`, are stored only under `restricted/<provider>/...`, remain `review`/non-production assets, and are never learner-eligible by default. Exact-content or safe-SVG visual duplicates append provenance to the existing logical asset without another byte copy. Unknown, non-commercial, and no-derivatives candidates remain fail-closed and are not downloaded or stored.

SVG inputs must be structurally screened before storage. Scripts, event handlers, embedded/remote resources, data URLs, and CSS imports are rejected. The local storage abstraction accepts only relative keys contained under its configured root.

## Learner retrieval

Authenticated callers can query `GET /educational-assets` with optional `query`, `subject`, `topic`, `grade`, `assetType`, and bounded `limit` filters. Results expose `assetKey`, a Kitabu-relative `assetUrl`, educational metadata, and display attribution. `GET /educational-assets/:assetId/file` serves only the eligible locally stored file with its persisted MIME type.

The query contract also supports `subtopic`, `providerKey`, exact `license`, `visualType`, and `curriculumUnitId`. Full-text `query` searches canonical title, subject/topic/subtopic, description, keywords, synonyms, visual type, canonical provider key, and canonical source license. Exact title/topic matches remain ranked first. Learner queries remain production-gated: requested restricted, rejected, or unverifiable license values return no learner assets.

Both endpoints apply the production eligibility policy: only approved CC0/public-domain, MIT, or CC BY assets are visible or read. The service never includes source URLs in learner responses. Remote source URLs remain immutable provenance records only and are never learner-serving URLs.

## Storage backends

Educational assets use the same repository-local storage convention as TTS, independently configured with `KITABU_EDUCATIONAL_ASSET_STORAGE_BACKEND=local|http-put`, `KITABU_EDUCATIONAL_ASSET_STORAGE_ROOT` (default `./var/educational-assets`), `KITABU_EDUCATIONAL_ASSET_STORAGE_UPLOAD_URL_TEMPLATE`, and `KITABU_EDUCATIONAL_ASSET_STORAGE_PUBLIC_BASE_URL`. Local storage enforces relative-key containment. HTTP-PUT uploads substitute the encoded storage key into `{key}` and send the persisted asset MIME type as `Content-Type`; learner reads use only the configured public base URL and persisted storage key. HTTP-PUT mode requires an upload template for imports and a public base URL for learner reads. Neither backend uses remote provenance URLs for learner delivery.

Normal local imports write the exact content-addressed key before the database insert. If that insert fails, the importer performs a best-effort removal of only that newly-created, path-contained key and rethrows the database error; a pre-existing object at the same key is never removed. HTTP-PUT intentionally does not issue a generic `DELETE`, so remote orphan cleanup remains the responsibility of the object-storage lifecycle/operations policy.

Migration `086_educational_asset_storage_backends.sql` extends the asset storage backend constraint to `local` and `http-put`; it is additive and does not rewrite existing rows. Apply migrations only through the documented migration runner and its safety gate. No object-storage credentials or provider downloads are part of this change.

## Acquisition adapters

Adapters implement bounded discovery and download using `RemoteAsset` provenance metadata, resumable cursors, and explicit capabilities. The runner supports `--limit`, `--dry-run`, `--resume`, bounded retries, content-hash and provider-asset identity deduplication, checkpointed import runs, and local-original storage. It validates file bytes before persistence; SVGs receive the structural safety check. Normalization and thumbnails are not implemented in this phase.

### PubChem on-demand resolution

`PubChemResolver` is an internal-only helper using the official [PUG REST API](https://pubchem.ncbi.nlm.nih.gov/docs/pug-rest). `lookupByName(name)` retrieves a CID and available Title, IUPAC name, molecular formula, InChIKey, and canonical SMILES, then constructs the official CID page and 2D PNG URLs. Lookup does not download the PNG. `downloadPng(candidate)` is a separately called, single-request operation with a timeout and User-Agent. Callers may inject a cache implementing candidate-metadata and PNG-byte storage; deterministic name/CID/PNG keys are used, candidate dates are stored as ISO strings, and cache hits avoid upstream requests.

PubChem is not a bulk acquisition adapter and has no learner route. Every lookup candidate is explicitly `UNKNOWN` with `needs-review` license status because PubChem aggregates contributor data and source licensing must be checked before any import or publication. The optional `PubChemSingleAssetAdapter`/`pubChemCandidateToRemoteAsset` bridge accepts one candidate only when the caller supplies an explicitly verified supported license, HTTPS license-evidence URL, and required attribution; it emits stable `pubchem`/`cid:<number>` chemistry-structure metadata and downloads only that candidate's official PNG. UNKNOWN, needs-review, rejected, missing-evidence, or non-official URLs are refused. This does not make PubChem production-ready by default and there is no general PubChem CLI.

Structured provider metadata is retained in `educational_assets.metadata` as a JSON object (default `{}`), including PubChem CID, formula, IUPAC name, InChIKey, canonical SMILES, and retrieval time when supplied by the asset flow. This metadata is internal review/attribution data and is never projected to learner responses.

The CLI supports `health-icons`, `bioicons`, `tabler-icons`, `openmoji`, `game-icons`, `wikimedia`, and `phylopic`. Health Icons is CC0-eligible; Tabler and Bioicons' supported CC0/MIT/BSD/CC-BY subtrees are eligible only after normal review, while Bioicons CC BY-SA subtrees remain restricted; OpenMoji remains CC BY-SA restricted; Game Icons requires staff suitability review in addition to its attribution; and PhyloPic is limited to an explicit taxon query or node UUID with per-image license review. Health Icons uses only the official [repository](https://github.com/resolvetosavelives/healthicons), GitHub tree API, and raw GitHub file URLs. Discovery is limited to `public/icons/**` SVG/PNG files, retaining every upstream resolution rather than guessing which variants are redundant. Use `npm.cmd run assets:sync -w apps/api -- --provider health-icons --limit 10` or add `--dry-run` / `--resume <cursor>`. Do not run bulk syncs during builds, and do not commit downloaded assets to Git.

Tabler Icons is a separate MIT-licensed adapter verified against its official [repository and LICENSE](https://github.com/tabler/tabler-icons). It discovers only current official `icons/*.svg` and `icons/filled/*.svg` paths and records them as `generic-ui-concept` assets: they are interface and concept icons, not textbook scientific diagrams. Use `--provider tabler-icons`; do not use it to imply curriculum-specific scientific illustration.

OpenMoji uses the official [OpenMoji repository](https://github.com/hfg-gmuend/openmoji) and only exported `black/` and `color/` SVG/PNG paths. Its official [license](https://github.com/hfg-gmuend/openmoji/blob/master/LICENSE.txt) and [FAQ](https://github.com/hfg-gmuend/openmoji/blob/master/FAQ.md) identify graphics as CC BY-SA 4.0 and provide project attribution. Use `npm.cmd run assets:sync -w apps/api -- --provider openmoji --dry-run --limit 10` for bounded reporting. OpenMoji is restricted by the current policy, so sync never promotes it to unrestricted learner publication.

Game Icons uses only the official [game-icons/icons repository](https://github.com/game-icons/icons), direct contributor-directory SVG paths, and its [CC BY 3.0 license record](https://github.com/game-icons/icons/blob/master/license.txt). It preserves contributor-path attribution as `Icons made by {author}` and classifies these as `ICON`/`GENERAL`, not textbook diagrams. Use `npm.cmd run assets:sync -w apps/api -- --provider game-icons --dry-run --limit 10`. Discovery does not guess child suitability from icon names or categories; assets remain in review pending an explicit staff decision.

Wikimedia Commons uses the official [MediaWiki API](https://commons.wikimedia.org/w/api.php) only. It requires an explicit category and uses bounded `categorymembers` continuation plus `imageinfo`/`extmetadata` lookups; it does not scrape HTML or mirror Commons. Use `npm.cmd run assets:sync -w apps/api -- --provider wikimedia --category "Human anatomy" --dry-run --limit 3`. The adapter preserves the Commons page title, page/revision identity, source page/raw file URLs, MIME and dimensions, description, creator/credit, and license evidence. Commons category membership is never treated as a license: only explicit per-file metadata maps to the supported exact license values, while missing, ambiguous, or unsupported metadata remains `UNKNOWN`/needs-review and cannot become production eligible. Openverse remains separate and unimplemented.

PhyloPic uses the official [API](https://api-docs.phylopic.org/v2) at `https://api.phylopic.org` and the official [image usage guidance](https://www.phylopic.org/articles/image-usage). Discovery requires exactly one bounded `--query <taxon>` or `--node <UUID>`; an empty/default broad crawl is refused. Use `npm.cmd run assets:sync -w apps/api -- --provider phylopic --query eucalyptus --dry-run --limit 3` or `npm.cmd run assets:sync -w apps/api -- --provider phylopic --node <node-uuid> --dry-run --limit 3`. The adapter resolves the current API build, follows bounded pagination or embedded item links, preserves image UUID, taxon names, contributor/attribution, source page, and the official vector URL when available, then falls back to an official PNG only when necessary. It accepts only explicit per-image PDM as `PUBLIC-DOMAIN`, CC0 as `CC0-1.0`, CC BY 3.0/4.0 as the exact attribution licenses, and CC BY-SA 3.0/4.0 as restricted licenses. CC BY-NC, missing, malformed, or unsupported licenses remain `UNKNOWN`/needs-review and cannot become production eligible; no provider-wide license assumption is made. API and image redirects are host-validated, and source URLs are provenance only.

Bioicons is an active bounded adapter, not a global-license import. It discovers only SVGs beneath `static/icons/{cc-0,mit,cc-by-3.0,cc-by-4.0,cc-by-sa-3.0,cc-by-sa-4.0,bsd}/`, preserves the exact CC BY/CC BY-SA version from each directory, records the directory-specific license evidence and creator URL from the official [`authors.json`](https://github.com/duerrsimon/bioicons/blob/main/static/icons/authors.json) when available, and fails if GitHub reports a truncated tree. Both CC BY-SA versions remain discovered but restricted by the existing runner policy. The official [`static/icons/bsd/LICENSE`](https://github.com/duerrsimon/bioicons/blob/main/static/icons/bsd/LICENSE) is treated as BSD-3-Clause; other unsupported prefixes remain excluded. Use `npm.cmd run assets:sync -w apps/api -- --provider bioicons --dry-run --limit 10` for bounded discovery only.

BSD-2-Clause, BSD-3-Clause, and Apache-2.0 are Tier A production-eligible values. Their required notices/attribution must be retained (`educationalAssetAttributionRequired` returns true); existing CC, rejected, and unknown policy behavior is unchanged.

## Phase 4 manifests and reports

Each normal sync atomically writes `manifests/<provider>/<import-run-id>.json` under the configured educational-asset storage root. The JSON manifest records run identity/revision/cursor, import timestamp, and every source path with its hash (when downloaded), license, database asset ID (when created), outcome, normalization status, and optional `usageRestriction`. The command output includes a report with acquisition counters plus provider, license, media-type, and restricted-license breakdowns; import runs retain a `restricted_count`. Dry runs return the same manifest/report in memory and write neither database nor storage. Dry-run `licenseRestricted`/`wouldDownload` identify CC BY-SA candidates that would be isolated; `wouldPublish` means unrestricted license-eligible acquisition only and never means staff approval or learner availability. Unknown/needs-review and rejected candidates are not downloaded.

Original files remain authoritative. SVGs are structurally validated and recorded as `validated-original`; unsafe files are quarantined and never enter learner storage. Raster files are recorded as `needs-normalization`: the current dependency set has no image decoder/resizer, so thumbnails and raster normalization are deliberately deferred and must not be represented as complete.

## Normalization and visual identity boundary

The dependency-free normalization module reuses the SVG hostile-content policy, reads dimensions directly from valid PNG, JPEG, GIF, and WebP bytes, and records nullable width, height, aspect ratio, and SVG `visual_hash` metadata. Exact SHA-256 remains the logical content identity. A safe SVG receives a deterministic visual hash from conservative canonical text (whitespace and straightforward attribute ordering only); it is not a perceptual hash and does not make two arbitrary drawings equivalent.

Original storage keys are never overwritten. Safe SVGs are `validated-original`; `normalized-copy` is reserved for a future separately stored derivative. Valid raster originals remain `needs-normalization`; invalid bytes are quarantined. Learner serving continues to use the original local file unless a future reviewed normalized key is explicitly introduced.

Raster resize, raster conversion to WebP or AVIF, AVIF decoding, thumbnails, and true perceptual hashing require an approved image-processing dependency and remain deferred.

## Phase 5 classification and curriculum links

Assets have controlled `visualType`, subject/topic/subtopic metadata, keywords/synonyms, grade ranges, language/accessibility fields, and explicit normalization status. Creation derives bounded alt text from explicit `altText`, then the supplied description, then the required title; it normalizes whitespace, caps output at 500 characters, and never invents scientific claims or rewrites diagram labels. Learner results expose the resulting `altText`, never source URLs or physical storage keys. Provider-derived classifications are conservative only: Health Icons is `ICON`/`HEALTH`, Tabler is `UI_ICON`/`GENERAL`, and Bioicons uses `ILLUSTRATION` plus directory-derived labels. None are CBC curriculum mappings. `educational_asset_curriculum_units` is available for explicit reviewed links to existing `curriculum_units`; this phase creates no links or invented unit IDs.

Platform-admin curriculum linking is explicit and step-up protected: `GET /admin/educational-assets/:assetId/curriculum-links` reads links, and `PUT /admin/educational-assets/:assetId/curriculum-links` replaces the complete set. The PUT body is `{ "links": [{ "unitId": "<existing curriculum_units UUID>", "relationshipMetadata": {} }] }`; an empty list clears the asset's links. Relationship metadata must be a JSON object no larger than 4,000 bytes. The repository also provides internal list/add/replace/remove helpers with foreign-key and existence checks. The API accepts only staff-supplied existing unit IDs; it never invents mappings from provider, subject, topic, filename, or asset type. Mutations require `platform_admin` step-up authentication and create an audit-log entry. These routes are not learner-facing, and learner responses remain unchanged.

### Controlled taxonomy links

Educational assets also support explicit many-to-many taxonomy links through `educational_asset_taxonomy_terms` and `educational_asset_taxonomy_links`. Terms have stable lower-case codes, display names, and an optional parent term; the additive seed includes broad subjects plus reviewed examples such as `biology.anatomy`, `biology.cells`, `biology.genetics`, `physics.forces`, `physics.machines`, `physics.electricity`, `lower-primary.animals`, `lower-primary.foods`, `lower-primary.transport`, and `lower-primary.weather`. The taxonomy is controlled data, not a provider catalogue.

Platform admins can read the controlled term list with `GET /admin/educational-assets/taxonomy-terms`, read one asset's links with `GET /admin/educational-assets/:assetId/taxonomy`, and replace the complete set with step-up-protected `PUT /admin/educational-assets/:assetId/taxonomy`. The exact PUT body is `{ "links": [{ "termCode": "biology.cells", "relationshipMetadata": { "reviewed": true } }] }`; `{ "links": [] }` clears all links. Term codes must be existing lower-case controlled codes, duplicate codes are rejected, and relationship metadata must be a JSON object no larger than 4,000 bytes. The mutation is transactional, platform-admin-only, rate-limited, and audited as `educational_asset.taxonomy_replaced`.

No taxonomy mapping is inferred or auto-created from provider names, filenames, directory paths, visual types, AI output, or curriculum guesses. Staff must supply existing seeded term codes explicitly. Taxonomy links are not added to learner responses or offline manifests in this slice.

## Multi-source provenance and attribution

One logical asset may retain multiple provenance records when byte-identical imports arrive from different sources. Provenance now has its own UUID identity; provider/source identity remains unique for idempotency. Existing duplicate provider identities are not silently removed: migration stops for manual provenance review before adding that uniqueness guarantee. Asset retrieval selects a deterministic canonical source (accepted license first, then newest retrieval, then stable ID) so learner results never duplicate the logical asset. Each retained record may also carry the original filename, creator, creator URL, exact license version, and raw license-evidence text when the provider supplies them; `licenseEvidenceUrl` remains the evidence URL. These fields are immutable provenance metadata and are not learner-projected. Internal callers can use `getAttributionsForAssets(assetIds)` to generate all source-name/license/attribution records. It intentionally returns no source URLs and is not exposed as a learner-facing endpoint.

## Staff review and offline references

`PATCH /admin/educational-assets/:assetId/classification` requires platform-admin step-up authentication and permits bounded edits only to `visualType`, `subject`, `topic`, `subtopic`, `keywords`, `synonyms`, `gradeMin`, `gradeMax`, `language`, `containsText`, `altText`, and `educationalDescription`. Omitted fields are preserved, explicit nullable values are supported where the schema allows them, and alt text is normalized and safely derived. The route cannot edit provenance, provider, license, storage, content hashes, or production status. It is rate-limited and creates an audit entry containing only safe field names/counts and classification metadata, never raw provenance or storage details.

`GET /admin/educational-assets` is restricted to `platform_admin` and lists all assets with their production status, retained review reason, and canonical attribution summary. `GET /admin/educational-assets/:assetId` is the platform-admin detail projection: it includes the retained source page/raw URL, provider/source identity, exact license and evidence URL/text, creator/attribution, original filename, classification, review reason, structured metadata, and stored MIME/byte/hash/dimension metadata. It intentionally omits the physical storage key/path and provides the internal preview URL `/admin/educational-assets/:assetId/preview` instead. `GET /admin/educational-assets/:assetId/preview` is also platform-admin-only, reads the persisted Kitabu storage key, serves the persisted MIME type with `private, no-store`, and permits draft/review/approved/rejected assets for staff inspection; storage failures return a safe 404. `PATCH /admin/educational-assets/:assetId/review` requires platform-admin step-up authentication and accepts `approved`, `rejected`, or `review`; rejected assets require a 1–500 character reason. Successful mutations create an `educational_asset.reviewed` audit entry. None of these raw provenance or preview fields are added to learner responses or offline manifests. The learner file route remains production-eligibility-gated and never reads unapproved storage.

Internal lesson/package preparation can call `getOfflineEducationalAssetReferences(assetIds)`. It returns only approved, license-eligible records with an immutable asset ID, Kitabu learner file URL, MIME type, byte size, SHA-256, title, alt text, canonical license, and provider/source-name attribution labels. It returns no remote source URL or physical storage path and does not create a bundle or download files. `createEducationalAssetOfflineManifest(manifestId, references)` projects those records into the existing runtime-contracts `AssetManifest` shape, using `kitabu://educational-assets/<asset-id>` as the internal URI, lower-case content hash, canonical license ID, and non-URL provenance labels. `manifestId` is the lesson/package binding held by the caller because AssetManifest v1 has no manifest-ID field. Lessons and scenes therefore bind this manifest to immutable educational asset IDs; offline download resolves the internal URI and verifies the recorded content hash. Learner endpoints remain limited to approved, eligible assets, so rejection immediately removes an asset from learner projections.

## Coverage reporting and migration safety

Run the read-only readiness preflight with `npm.cmd run assets:preflight -w apps/api`. It loads `apps/api/.env`, inspects the configured PostgreSQL database and numbered SQL files, reports pending migrations and destructive safety blockers, checks the educational-assets and `curriculum_units` tables, and reports the configured local storage root. It prints an operator JSON report and returns non-zero when the database is unreachable, `schema_migrations` is absent, required tables are missing, or a pending migration matches the migration runner's destructive safety patterns. The preflight never creates `schema_migrations`, applies or baselines migrations, writes storage, downloads assets, or changes database state.

`createEducationalAssetCoverageReport(observations, expectedAreas, { weakBelow })` is a pure planning helper. It counts only explicit subject/topic observations (or their supplied counts) against a caller-controlled expected subject/topic list, then reports actual, weak, and uncovered areas. It does not infer curriculum coverage from provider names, filenames, or adapter metadata.

The documented local migration command is `npm.cmd run migrate -w apps/api`. The default safety gate can stop at legacy destructive migrations. After an approved backup/restore decision, run exactly `$env:KITABU_ALLOW_DESTRUCTIVE_MIGRATIONS='true'; npm.cmd run migrate -w apps/api` in that approved local maintenance session; do not use this override for routine imports.
