# Kitabu full-funnel analytics specification

This is the backend contract for the later website and Expo instrumentation stages. The canonical implementation is `apps/api/src/analytics.ts`; the first-party store is introduced by migration `100_full_funnel_analytics.sql`, with authoritative current consent added by the unapplied migration `101_analytics_consent_states.sql`, durable delivery leases by `102_analytics_delivery_leases.sql`, and once-per-episode inactivity state by `103_analytics_inactivity_state.sql`.

## Canonical events

`page_view`, `landing_page_engaged`, `app_download_clicked`, `first_open`, `signup_started`, `signup_completed`, `profile_setup_started`, `onboarding_completed`, `first_tutor_session`, `learning_session_completed`, `pricing_viewed`, `checkout_started`, `payment_not_completed`, `purchase`, `subscription_renewed`, `purchase_refunded`, `subscription_expired`, and `user_inactive`.

Properties are event-specific and minimized. The backend drops every unknown property and sensitive/free-form value. Allowed examples include page path/title, bounded engagement type, store placement/platform/destination class, source page, role, exact Kitabu grade, subject, plan code, billing cycle, amount in KSh cents, payment method, provider, and bounded failure code. The marketing website has no exact child-grade field. Names, email, phone, school, tutor content, answers, credentials, and raw learner identifiers are never accepted into the canonical properties.

Every event has a UUID `eventId`, bounded ISO `occurredAt`, UUID `anonymousId`, optional UUID `sessionId`, `platform`, `source`, optional app version, strict consent flags, and optional first-touch attribution fields (`utm_*`, referrer, `fbclid`, `gclid`, `ttclid`). Anonymous events may be associated with the authenticated account later; first attribution is preserved and latest attribution is replaced per event.

## Surfaces and flow

The website stage fires `page_view` once per canonical page, `landing_page_engaged` once per page/session at 10 seconds, 30% scroll, or meaningful CTA/form engagement, `app_download_clicked` only for direct Google Play destinations, and `pricing_viewed` when a tagged pricing card meaningfully intersects. School-demo form engagement remains PII-free analytics; submitted contact details go only through the existing lead delivery path. Mobile stage 3A provides the consent-gated first-party foundation in `native-app/src/services/mobileAnalytics.ts`: first-open-once per consent lifecycle, bounded AsyncStorage retry queue, anonymous-to-user association through authenticated headers, install/deep-link attribution, and exact internal grade handling. Stage 3B wires success-only signup, onboarding, first-tutor, pricing, and checkout events. Stage 3C wires `learning_session_completed` only after persisted progressive lessons, homework assignments, weekly exams, or progressive diagnostics return success; generated/subject quiz and onboarding diagnostic completion remain unwired until their owning flow exposes a stable server completion ID. Native AppsFlyer attribution is implemented through the official 6.18.0 plugin in strict mode with manual start after analytics consent; Firebase, Meta, and TikTok native SDKs remain disabled, and Android Install Referrer remains a documented follow-up. The API accepts client batches at `POST /analytics/events`; bearer auth is optional, and an authenticated request links its anonymous ID to the account. Client requests may only identify `website`/`web` or `native`/`ios|android`.

The API stores the sanitized event before best-effort provider delivery. Delivery rows are retried by the bounded `analyticsWorker.ts` poller after migration `102_analytics_delivery_leases.sql` is deployed: claims use `FOR UPDATE SKIP LOCKED`, a short lease, bounded exponential backoff, and a maximum attempt count. Each retry re-reads authoritative consent and verified native roles; analytics withdrawal skips all pending destinations, marketing withdrawal skips Meta/TikTok, and native student/unknown rows never reach third-party providers. A claimed retry sends only its claimed provider. The worker is enabled by default but every poll is isolated so provider/database errors cannot stop TTS or account-deletion loops. The daily inactivity maintenance job uses a default seven full days without the latest canonical non-inactivity event or reliable presence evidence, persists one state row per user/episode, and emits only after current analytics consent is rechecked. It emits no event without consent, and server-side Meta/TikTok delivery requires a verified adult role; unknown/student roles remain suppressed. The inactivity event contains only `days_inactive` and a bounded canonical `last_surface`. Migrations 100, 101, 102, and 103 remain unapplied and must be applied in order through the normal production migration process. `POST /analytics/consent` stores current bounded consent separately from event history; later M-Pesa lifecycle events prefer this state and conservatively default analytics and marketing off when no state exists. Native student/unknown events remain first-party only, while eligible adult native roles require explicit consent for providers. Provider errors never fail an auth, learning, or payment request. Admins retrieve aggregate funnel rows from `GET /admin/analytics/funnel`, protected by the existing admin role, school context, step-up, and analytics rate-limit rules.

## Provider mapping and consent

PostHog receives analytics-consented events through `/i/v0/e/` on the configured regional ingestion host. Meta Conversions API maps standard events to `PageView`, `CompleteRegistration`, `ViewContent`, `InitiateCheckout`, and `Purchase`; TikTok maps to `ViewContent`, `CompleteRegistration`, `InitiateCheckout`, and `CompletePayment`; GA4 maps to `page_view`, `sign_up`, `view_item`, `begin_checkout`, and `purchase`. Other events use bounded PascalCase custom names for Meta/TikTok and bounded canonical names for GA4. Meta/TikTok/GA4 advertising payloads use only a SHA-256 pseudonymous `external_id` and never raw UUIDs, email, or phone. Website payloads carry a safe Kitabu page URL; native/server payloads use app/system action context.

Exact grade is retained for first-party/PostHog product analytics. For explicit marketing-consented parent-role events only, provider payloads derive a coarse `grade_band` (`1-3`, `4-6`, `7-9`, `10-12`) and never forward the exact grade. Student/minor-role advertising payloads contain neither exact grade nor grade band. Meta Conversions API and TikTok Events API receive only marketing-consented events. GA4 Measurement Protocol supplements client tagging and receives analytics-consented events; `client_id`/`app_instance_id` are retained only when supplied with analytics consent. Attribution cookies (`fbp`, `fbc`, `ttp`) are bounded and marketing-consent gated. No email/phone matching or hashing is performed. All provider credentials are server-only environment values.

Provider event IDs use Kitabu's UUID `eventId` for dedupe. Website batches declare a strict `clientDeliveredProviders` list; when GA4 is delivered by the consented browser tag, the server skips GA4 Measurement Protocol while retaining the first-party row. Meta and TikTok remain client + server deliveries using the same event ID for dedupe. Logs contain only event ID, canonical name, destination, safe properties, status, and error class; they never contain secrets or raw identity data.

## Consent and retention rules

Marketing forwarding requires explicit marketing consent. On the website, before analytics consent, anonymous/session IDs, attribution, and the offline queue remain memory-only; provider-cookie reads do not occur. On mobile, necessary-only remains usable and no analytics ID, attribution, queue, third-party SDK collection, or advertising identifier is created before analytics consent. AppsFlyer collection is disabled for student, unknown, and other non-eligible contexts; only an eligible adult/parent may enable the consent-gated AppsFlyer attribution/event projection. No iOS ATT prompt or advertising-identifier collection is active in this native integration. Analytics consent persists only the bounded identifiers and attribution needed for the first-party row. GA4 may load with analytics-only consent on the website; Meta, TikTok, and Google Ads require explicit marketing consent. First-party rows contain only the canonical minimized fields and consent state. Minors are included in the same minimization rule; no child name, school, content, answer, or raw learner identifier is forwarded to advertising providers. Consent changes synchronize best-effort to `POST /analytics/consent`; withdrawal sends the previous anonymous ID before deleting local optional identifiers, attribution, queue, and once-event markers, and remains locally effective if the server is unavailable. Re-opting in starts a new analytics-consent lifecycle, so `first_open` may be emitted once again; it is not a permanent install marker after withdrawal. Self-service account deletion removes linked analytics events, consent state, and associated anonymous IDs. The migration remains unapplied until the normal production migration process.

## Authoritative lifecycle rules

The M-Pesa callback remains authoritative. Only after the verified callback and database payment/subscription transition commit does the server queue `purchase` (success) or `payment_not_completed` (failure/cancellation). IDs are deterministic from the payment request and receipt/checkout ID, so repeated callbacks cannot duplicate lifecycle events. The server inherits the authoritative current account consent, attribution, anonymous ID, and consented GA4 identifiers; if no context exists, analytics and marketing default off. Exact grade is never part of payment properties. Existing Mufasa payment telemetry remains unchanged and is delivered independently. Renewal, refund, and expiry events remain future authoritative server jobs; inactivity is emitted by the daily maintenance job described above, never by client success claims.

Renewal, refund, and expiry events must be emitted by their authoritative server jobs/state transitions in a later stage; inactivity is emitted by the bounded daily maintenance job, and client success claims never create purchase events.

## Audiences and dashboard setup

The protected funnel retrieval supports aggregate grouping/filtering by role, grade band, subject, source, platform, campaign, and plan code. `GET /admin/analytics/funnel` defaults to the trailing 30 days and rejects ranges longer than 400 days; `from`/`to` are ISO timestamps. For example: `/admin/analytics/funnel?gradeBand=4-6&subject=Mathematics&source=website&format=json`, or the same query with `format=csv` for a spreadsheet-safe export. CSV output contains only event name, role, `gradeBand`, subject, source, platform, campaign, plan code, event count, and actor count; it has no user IDs, anonymous IDs, PII, or exact grades, and formula-like cells are neutralized. School admins remain restricted to their school; only the existing authorized platform-admin all-data path can omit school scope. The four ASCII bands are exactly `1-3`, `4-6`, `7-9`, and `10-12`; unknown/out-of-range grades are unbanded and never coerced into `10-12`. Intended audiences are landing visitors, engaged visitors, download clickers, opened app users, signup starters/completers, onboarded learners, first tutor users, active learners, checkout starters, paid subscribers, renewals, refunds, expiries, and inactive users. Parent-role marketing audiences may use only the coarse grade bands above; student/minor audiences must not be exported to ad platforms. Configure provider destinations only after server secrets, consent policy, event dedupe, and privacy review are verified. The website SDK is implemented in `apps/web/site-20260818.js`, and mobile first-party instrumentation is implemented in the Expo analytics service with consent-gated API delivery. Android AppsFlyer attribution uses the official 6.18.0 plugin in strict kids mode with manual start after analytics consent, Purchase Connector disabled, and AD_ID blocked; its bounded conversion/event projection excludes learner identifiers, role, grade, subject, and content. Dashboard/manual provider configuration remains required.
